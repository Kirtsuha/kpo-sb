# Async Orders & Payments (Kafka, Spring Boot)

Учебный проект с микросервисной архитектурой, демонстрирующий асинхронную обработку заказов и платежей с использованием Apache Kafka и шаблонов **Transactional Outbox / Inbox**.

Проект реализован в рамках ДЗ по курсу КПО.

---

## Архитектура

Проект состоит из трёх микросервисов:

```
Client
  ↓
API Gateway (Spring Cloud Gateway)
  ↓
+-------------------+      Kafka      +---------------------+
|  Orders Service   |  ───────────▶  |  Payments Service   |
|  (создание заказа)|  ◀───────────  |  (списание средств) |
+-------------------+                 +---------------------+
```

### Компоненты

- **Gateway**
  - единая точка входа (`localhost:8080`)
  - маршрутизация запросов
  - не содержит бизнес-логики и контроллеров

- **Orders Service**
  - создание и хранение заказов
  - отправка событий оплаты в Kafka (через Outbox)
  - обработка результатов платежей

- **Payments Service**
  - управление аккаунтами пользователей
  - списание средств
  - защита от повторных списаний (Inbox + idempotency)

- **Kafka**
  - асинхронный обмен событиями
  - семантика доставки *at-least-once*

- **PostgreSQL**
  - отдельная БД для каждого сервиса

## Асинхронное взаимодействие

Для обеспечения надёжности используются шаблоны:

### Transactional Outbox
- события записываются в БД в рамках транзакции
- отдельный publisher читает outbox и отправляет события в Kafka

### Transactional Inbox
- входящие события сохраняются в inbox
- повторная обработка одного и того же события невозможна

### Idempotency
- повторное сообщение Kafka **не приводит** к повторному списанию средств
- обеспечено уникальностью `order_id` и inbox-механизмом

## Точки входа

### API Gateway
```
http://localhost:8080
```

Все запросы от клиента должны идти **через Gateway**.

### Swagger UI (для отладки)
- Orders Service:  
  http://localhost:8081/swagger-ui.html
- Payments Service:  
  http://localhost:8082/swagger-ui.html

Swagger **не используется в Gateway**, так как он не владеет API-контрактами.

## Проверка работоспособности (через Postman)

### Заголовки
Во всех запросах:
```
X-User-Id: u1
Content-Type: application/json
```

### 1. Создание аккаунта
```
POST /payments/account
```

### 2. Пополнение баланса
```
POST /payments/topup
Body: { "amount": 1000 }
```

### 3. Создание заказа
```
POST /orders
Body: { "amount": 300, "description": "test order" }
```

Ответ:
- сразу: `status = NEW`
- через 1–3 секунды: `FINISHED` или `CANCELLED`

### 4. Проверка баланса
```
GET /payments/balance
```

Баланс уменьшается только при успешной оплате.

## Обработка ошибок

Проект использует единый формат ошибок и корректные HTTP-коды:

| Ситуация                    | Код |
|-----------------------------|-----|
| Ресурс не найден            | 404 |
| Ошибка валидации            | 400 |
| Недостаточно средств        | 409 |
| Внутренняя ошибка сервиса   | 500 |

Пример ответа:
```json
{
  "timestamp": "2025-01-01T12:00:00Z",
  "status": 404,
  "error": "Not Found",
  "message": "Order not found",
  "path": "/orders/...",
  "traceId": null
}
```

## Примечания

- Gateway не содержит `@RestController` — он выполняет только маршрутизацию.
- Swagger размещён только в микросервисах, так как именно они владеют API.
- Проект демонстрирует асинхронную архитектуру, а не синхронные REST-вызовы между сервисами.
